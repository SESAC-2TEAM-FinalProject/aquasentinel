# ADR-0001 — EKS API 공개 엔드포인트를 CIDR 로 제한하지 않는다

- **상태**: 채택 (팀 결정 2026-10-26 「(ㄱ) 제한하지 않음」 · 이 문서 2026-10-27 A(원주) 작성)
- **대상**: `terraform/modules/aws-eks` 를 쓰는 모든 클러스터 — 현재 서울 `seoul/rebuild/2-cluster`, 도쿄 `tokyo/rebuild/2-cluster`
- **왜 이 문서가 있는가**: 모듈이 스스로 요구한다 — `modules/aws-eks/variables.tf:33` · `README.md:57` 「8주 프로젝트라 VPN/bastion 없이 public 으로 시작한다 — **반드시 ADR 로 사유를 기록할 것**」
- 표기: `[사실]` 실측 / `[추론]` 실측에서 계산 / `[제안]` 제 의견(결정 아님)

## 1. 맥락 — 지금 코드와 실물이 이렇다

| 항목 | 값 | 근거 |
|---|---|---|
| 모듈 기본값 | `endpoint_public_access = true` · `endpoint_private_access = true` | `modules/aws-eks/variables.tf:32·38` · `main.tf:86-87` `[사실]` |
| 🔴 `public_access_cidrs` | **변수 선언도 사용처도 없다** — 코드로 쓰인 곳 **0건**(문자열 검색은 1건 걸리는데 그건 `tokyo/runner/main.tf:186` 의 **주석**, 즉 이 사실을 적어둔 줄이다) | `grep -rn public_access_cidrs terraform/ \| grep -v '^[^:]*:[0-9]*: *#'` `[사실]` |
| 그래서 적용되는 값 | AWS 기본 **`0.0.0.0/0`** | `[추론]` — 변수가 없으니 AWS 기본값이 쓰인다 |
| 서울 실물 | `PublicAccess=true` · `PrivateAccess=true` · `PublicCidrs=["0.0.0.0/0"]` | `aws eks describe-cluster`(2026-10-27) `[사실]` |

즉 **"제한하기로 했다가 안 한 것"이 아니라, 제한하는 수단 자체가 코드에 없다.** 이 ADR 은 그 상태를 의식적으로 유지하겠다는 기록이다.

---

## 2. 결정

**EKS API 엔드포인트를 공개로 두고 CIDR 로 제한하지 않는다. 접근 통제는 네트워크가 아니라 IAM + EKS Access Entry 에 둔다.**

---

## 3. 왜 — 네 가지

### 3.1 🔴 도쿄 DR 러너가 이것에 의존한다 (2026-10-27)

`tokyo/runner` 는 재해 때 도쿄를 세우는 유일한 수단이다(`runbooks/도쿄러너_재해때_깨우기.md`). 그 러너가 도쿄 EKS API 에 닿는 방법이 **공개 엔드포인트뿐**이다.

- 서울 러너는 클러스터 SG 에 인그레스 규칙을 더해 사설 엔드포인트로 간다(`global/runner/main.tf:208`)
- 🔴 **같은 수를 도쿄에 쓸 수 없다** — SG 참조(`referenced_security_group_id`)는 **같은 리전의 같은/피어링된 VPC** 에서만 된다. 도쿄 러너는 기본 VPC(`172.31.0.0/16`), 도쿄 EKS 는 재구축 VPC(`10.1.0.0/16`) 다 `[사실]`
- 제한하면 러너에 **고정 EIP** 가 필요해지고, EIP 가 바뀌면 **재해 중에 CIDR 을 고쳐야 한다** — DR 절차에 "지금 AWS 콘솔에서 허용목록을 고친다" 는 칸이 생긴다 `[추론]`

### 3.2 VPN·bastion 이 없다

계획서가 8주 범위에서 VPN/bastion 을 세우지 않기로 했고(모듈 README 가 인용하는 계획서 9절·11.5절), 지금도 없다 `[사실]`.

### 3.3 팀원 접근 주소가 고정이 아니다

3인이 각자 로컬에서 `kubectl` 을 쓴다. 집·카페·테더링 주소는 고정 IP 가 아니라 CIDR 허용목록이 **매번 깨진다** `[추론]`.

### 3.4 🔴 공개 ≠ 무방비 — 실제 통제는 IAM 이다

엔드포인트가 열려 있어도 EKS API 는 **AWS SigV4 서명 + Access Entry** 가 있어야 들어온다. 2026-10-27 실측으로 들어올 수 있는 주체는 **8개뿐**이다 `[사실]`:

| 주체 | 무엇 |
|---|---|
| `aquasentinel-dev-eks-node-role` | 노드 |
| `aquasentinel-gitlab-terraform-apply` · `-plan` | CI |
| `aquasentinel-gitlab-alert-maintenance` | 알람 점검 |
| `aquasentinel-member-jaehee` · `-changyoung` | 팀원 |
| `AWSServiceRoleForAmazonEKS` | AWS 서비스 |
| `user/sesac13` | 계정 사용자 |

`authenticationMode` 는 **`API_AND_CONFIG_MAP`** 이고, `aws-auth` ConfigMap 에는 **노드 역할 하나만** 들어 있다 `[사실]`.

---

## 4. 대가 — 이것을 감수한다

### 4.1 🔴 감사 로깅이 꺼져 있어 "누가 두드렸는지" 를 볼 수 없다

2026-10-27 실측 — 컨트롤 플레인 로그 **5종(`api`·`audit`·`authenticator`·`controllerManager`·`scheduler`) 전부 `enabled: false`** `[사실]`.

🔴 **모듈에 `enabled_cluster_log_types` 설정이 아예 없다** — `grep -rn enabled_cluster_log_types terraform/` **0건**(주석 포함) `[사실]`. → 끄기로 **결정한 게 아니라** AWS 기본값이 그대로 남은 것이다.

그래서 "엔드포인트는 열어두되 이상 접근은 로그로 본다" 는 흔한 보완책이 **지금은 성립하지 않는다.** 이 ADR 에서 가장 약한 칸이다.

### 4.2 엔드포인트가 전 세계에서 관측된다

인증 없이는 들어오지 못하지만, 클러스터가 **존재한다는 사실과 주소**는 누구나 볼 수 있다. 무차별 인증 시도의 대상이 되고, 그 시도가 로그에 남지 않는다(4.1).

### 4.3 IAM 자격증명 유출이 곧 클러스터 접근이 된다

네트워크 경계가 없으므로 **키 하나가 유출되면 바로 API 에 닿는다.** 사설 엔드포인트였다면 유출 + 네트워크 진입 두 가지가 필요했을 것이다 `[추론]`.

## 5. 기각한 대안

| 대안 | 왜 기각했나 |
|---|---|
| **(a) CIDR 허용목록** | 🔴 모듈에 변수부터 신설해야 하고, 도쿄 러너에 고정 EIP 가 붙어야 하며, 팀원 주소가 비고정이라 **매번 깨진다**. 결정적으로 **재해 중에 허용목록을 고치는 절차**가 생긴다(3.1) |
| **(b) 사설 전용 + VPN/bastion** | 8주 범위 밖(3.2). 그리고 도쿄 러너가 기본 VPC 에 있어 **VPC 피어링까지** 필요해진다 |
| **(c) 사설 전용 + 러너를 재구축 VPC 안으로** | 🔴 **순환이 재발한다** — 도쿄를 내릴 때 러너도 사라지는데, 그 러너가 도쿄를 다시 세워야 한다 |

---

## 6. 재검토 조건 — 이 중 하나면 다시 연다

1. **실사용자 데이터가 들어온다.** 지금은 가상 사용자 기반이라 유출 피해 범위가 작다는 전제가 깔려 있다(모듈 README 가 인용하는 계획서 18.3절)
2. **판정 창이 끝난다**(2026-11-10). 창 안에는 `4-edge`·클러스터를 건드리지 않기로 했으므로 어떤 보완도 창 뒤다
3. **고정 egress 가 정리된다.** 도쿄 러너 EIP·NAT 주소가 고정되면 (a) 의 비용이 크게 떨어진다
